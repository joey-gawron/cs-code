# Known issues found during integration (not fixed yet)

* **First-run retention of a closed window** (found 2026-10-31 by WindowlessRunTests, macOS): in a brand-new CsCode home, the first
  application-scope state write (the layout saved as the window closes) creates `data/globalStorage` while file watches wait in the home
  directory for folders below `data/` (themes, snippets, ...) to appear. After that, a closed window's MainWindow, container and shell stay
  reachable after `AppShutdown.RunAsync` disposed the container; no static field reaches them (a native or IO-lane-thread root: likely a watch
  backend whose `Dispose` was posted to the IO lane by `FileWatcher.Dispose` and cancelled by `IoLane.Dispose`, which drops queued items).
  A home that has run CsCode before (the data folders exist) does not show it, and before macOS kept the process after the last window
  closed the process ended anyway. The leak test creates `data/globalStorage` first; the watcher shutdown needs a look by the Platform owner.

* **Editor PerfMemoryTests 10 MB open budget (4.5x) fails inside the full Editor.Tests run** (6.4x on integration, 5.9x on the editor agent's own branch 62b9445), passes alone (2.6x) and when only PerfMemoryTests runs. Serializing the class did not help; the following 1 MB case reads -85 MB, so earlier cases' memory is released lazily during later measurements. Pre-existing, order-dependent; belongs to the parked memory-profiling wave (do not loosen the budget).
* **Editor TextMateTests.Tokenisation_happens_on_the_editor_worker...** stalls under full-suite load ("tokenised 58/300 lines in 30000 ms"); passes alone. TokenizationSession.RunSlice waits for a UI Changed handler the test never pumps. Load-dependent.
* **Panels.Search SettingsViewModelTests.Invalid_numbers_show_an_inline_error_and_are_not_written("101")**: flaky (fails some full runs, also on 44bc116).
* **Panels.Search HostileTests.Cancelling_a_search_of_200k_files...** assumes the scan is still running after 400 ms; a fast machine finishes it in ~310 ms. Needs a bigger tree or a cancellation trigger that does not depend on elapsed time.
* Closed after the 2026-10-29 fix merge: the 300-tab live dock retention test (Dock's ControlRecycling cache; fixed by the shell lifecycle and wiring branches) and the 2 real netcoredbg failures (the adapter has no hit-count breakpoints or logpoints; the tests now assert they are reported unsupported).
* **Dap SessionTerminationTests.Stop_prefers_terminate_when_supported_then_disconnects**: races the fake adapter's command record ('disconnect' missing when asserted); fails in full Dap runs, passes alone 4/4.
* **App ResponsivenessTests storms** fail under machine load (load average ~4, e.g. while agents build); they fail the same way on older commits. Environmental.
* **Debug Console 1M one-console.log-per-line flood** misses the UI budget (p99 17-25 ms, max 53/70 ms once each): DEFERRED by the user to the performance/profiling wave (2026-10-29). The RealJsDebugResponsivenessTests one-per-line case may fail until then.
* **App ThemeSwitchingCostTests preview-rate budget** fails on main 2a9226e: the theme dropdown was merged before its review finished, at the user's request; the original session corrects it.
* **App ThemeSwitchingCostTests.A_hundred_theme_switches_leave_the_managed_heap_flat_and_rebuild_nothing** (not the preview-rate budget above) failed once in a full App run on macOS under load (mac/app-tests f113d5d): "textmatesharp.atom-one-light was not applied" within its 5 s wait, inside the 100-switch loop; it passes alone. One cause is fixed on mac/app-tests: the shell's follow-up of a `workbench.colorTheme` change, reported after the next switch while settings.json was still being written, chose and persisted the previous theme again (ThemeDropdownTests.A_late_report_of_the_previous_choice... covers it). If it recurs, look for a stalled apply (thread-pool starvation delaying ThemeApplier's prepare or its burst timer) rather than raising the wait.
* **App timing budgets under load on macOS**: in a full App run beside another agent's App tests (mac/app-tests f113d5d), BackgroundSessionProcessTests.Latency_resident_show_and_warm_spare_claim_are_within_budget failed with "warm-spare open took 535 ms (budget 500 ms)" and MacroRealAppTests.Playing_ten_thousand_times_in_the_real_editor_stays_within_the_ui_budget with slice p99 5.35 ms against 4 ms on its third attempt. Both pass alone (2026-10-30). Environmental, like the ResponsivenessTests storms; do not loosen the budgets.
* **Load-sensitive on macOS (full-solution run while other agents build; each passes alone 3/3 or more)**: Panels.Debug `ConsolePumpTests.The_producer_side_only_enqueues_and_a_flood_stays_bounded` (one Enqueue stalled 194 ms against a 20 ms budget: a preempted or GC-paused caller), MemoryTests `ToolkitTests.ResponsivenessProbe_measures_queue_latency_and_sees_a_blocked_thread` (calm p99 10 ms against 5 ms), Panels.Terminal `RealAppTaskTests.A_pre_launch_task_runs_in_a_terminal_before_the_debugger_starts` (6/6 alone; in the full run the task terminal had CsCode's own header and footer but not the shell's `hello-from-42`, so the task's output was lost or not yet delivered: worth a look at the macOS PTY exit drain, UnixPtyHost.ExitDrainTime 150 ms, if it recurs).
* **App BackgroundSessionProcessTests on macOS**: `Cold_start_without_a_spare_opens_the_session_and_reports_its_latency` and `Concurrent_launches_of_one_session_start_one_process` fail, and the class's other "no process left" checks pass vacuously: SessionProcessHarness.ProcessesOfThisHome finds processes by CSCODE_HOME in /proc/<pid>/environ, and macOS shows no other process's environment (ps -E and KERN_PROCARGS2 return none). Needs another way to tell this harness's processes (e.g. a marker the launcher passes on to the processes it starts, or the runtime directory's endpoints plus a process-name scan).
* **Editor PerfMemoryTests.A_big_file_stays_scrollable_and_editable_in_large_file_mode fails on macOS (arm64), also alone**: typing in the 12 MB file has a p99 of 28-47 ms against its budget (36.6 and 37.4 ms in two runs alone on 2026-10-30). A real macOS performance gap, not load; belongs to the performance/profiling wave. Do not loosen the budget.
* **Full-suite timing budgets on macOS under load** (2026-10-30, while a Linux VM and other agents were building): BackgroundSessionProcessTests.Latency_resident_show_and_warm_spare_claim_are_within_budget, MacroRealAppTests.Playing_ten_thousand_times..., MemoryTests AppSoakTests.Typing_into_a_document_and_closing_it_without_saving and ToolkitTests (ResourceCensus, ResponsivenessProbe), and MacFileWatcherTests.A_recursively_watched_directory_replaced_in_an_instant... failed in the full run and pass alone (2/2). Environmental.
* **Panels.Debug RealDebuggerEndToEndTests.The_panels_show_what_the_real_adapter_reports_through_a_whole_debug_session fails on macOS (arm64)**: "Condition not reached in time: stopped at the breakpoint" (41 s), alone too, on main and on fu/debugger-small (2026-10-30). It does not skip where netcoredbg is fetched: FindNetCoreDbg walks up from the test binary, so a worktree under `.claude/worktrees/` finds the main checkout's `.scratch/tools/netcoredbg` (netcoredbg 3.2.0-1092, an arm64 build). The debuggee never reports the breakpoint hit; not yet investigated (a breakpoint the adapter leaves unverified on macOS, or the launch itself, are the first things to look at).
* **Platform LocalFileSystemTests.Cancelling_mid_write_leaves_the_original_untouched** failed once (13 ms) in a full Platform run on macOS on 2026-10-30 while other builds ran; it passed 5/5 alone with its class. Timing-sensitive; watch for it.
