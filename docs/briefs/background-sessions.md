# Module brief — Background mode + saved sessions (hot-loaded windows) — **wave 3** (after waves 1 & 2a are merged)

**User request (2026-10-29):** "leave cscode running in the background so I can hot load a window with a saved session."

**Owns (when launched):** `src/CsCode.Sessions/**` (Avalonia-free: session model, store, hot-exit backups, IPC protocol, session broker logic), `tests/CsCode.Sessions.Tests/**`, additive glue in `src/CsCode.App/Background/**` (window lifecycle, tray, CLI client mode), additive `IEditorViewController` view-state use, `tools/autostart/**`, `docs/SESSIONS.md`. Read `docs/briefs/00-common.md` first — rules, threading and memory sections apply.

## Definitions
* **Session** = a named, persisted workspace state: workspace folders (local or `ssh://` remote), open editors (URI, group, order, pinned/preview, active), per-editor **view state** (caret, selections, scroll, folds), dock layout, active tool windows, breakpoints + watches (already per-workspace in Dap — reference, don't duplicate), search/palette history, Vim registers/marks (if `vim.persistRegisters`), **unsaved buffers via hot exit** (dirty content backed up so a session restores without save prompts, like VS Code's hot exit), window bounds/monitor/maximised state.
* **Resident session** = a background CsCode process that owns one session and keeps it warm: its window is *hidden*, not destroyed; documents, undo stacks, language servers, file watchers and (optionally) debug sessions stay alive. **Hot load** = showing that window again.
* **Warm spare** = a background process that has finished runtime/Avalonia/service start-up but has no session yet; opening a new or non-resident session *claims* it (and a new spare is spawned), so even "cold" sessions open fast.

## Architecture decision: one process per session (+ one warm spare), coordinated over per-user local IPC
Rationale: today every Core service is a process-wide singleton bound to one workspace (`IWorkspaceService`, `INavigationService`, `IDocumentManager`, …). Making them window-scoped for multi-window-in-one-process is a large, risky refactor; one process per session reuses everything unchanged, isolates sessions (a hung language server in one session can't touch another — consistent with the threading/isolation rules), and lets the OS reclaim a session's memory completely when it is evicted. Hot load cost becomes "make an existing window visible" (target **< 150 ms** from `cscode` invocation to a painted, interactive window).

```
 cscode (CLI / desktop entry / tray) ──local IPC──► session process "work"   (window hidden or shown)
                                     ──local IPC──► session process "oss"    (hidden, trimmed)
                                     ──local IPC──► warm spare (no session; claimed on demand, then replaced)
```
* **IPC**: one Unix-domain socket per process in `$XDG_RUNTIME_DIR/cscode/` (mode 0700; verify peer UID via `SO_PEERCRED`) — Windows: named pipe with a current-user-only ACL; macOS: socket under `$TMPDIR`. Tiny length-prefixed JSON protocol: `hello` (version, pid, session, state), `show {paths?, line?, waitUntilClosed?}`, `hide`, `claim {session}`, `listSessions`, `quit {force}`, `focusFile`. No network listeners, ever. Stale sockets (dead pid) are detected and removed. Per-session **lock file** prevents two processes owning one session (race: two `cscode --session x` at once).
* **Launcher logic** (in the same executable, "client mode", chosen before Avalonia initialises so it stays ~50 ms): `cscode [--session NAME] [paths…]` → find the process owning NAME → `show` (+ open the paths) → exit 0; else claim the warm spare (`claim NAME`) → else start a new process `--session NAME`. `cscode` with no session = the last active session (setting `cscode.sessions.default`: `last` | `new` | a name). `--new-window` = new unnamed session. Also: `--list-sessions`, `--background` (start/ensure the spare + resident sessions without showing a window; for login autostart), `--quit [NAME|--all]`, `--wait` (block until that file's tab closes — for `git commit` editor use).
* **Closing a window** hides it (process stays resident) when `cscode.background.keepRunning` = `true` (default **true** on Linux/Windows, **true** on macOS where it matches platform convention); *File ▸ Quit Session* actually exits that process after persisting; *File ▸ Exit All* quits every CsCode process. Dirty buffers never block hiding (hot exit backs them up); quitting a session with dirty buffers follows `files.hotExit` (`onExitAndWindowClose` default → back up, no prompt).
* **Tray icon** (Avalonia `TrayIcon`; the desktop exposes a StatusNotifier host — verified present on this machine): menu with resident sessions (state, memory), *Open session ▸ …* (saved ones), *New window*, *Quit all*; click → show last session. Respect `cscode.background.showTrayIcon`. Without a tray host the feature still works via the CLI/desktop entry.
* **Eviction & resource policy for hidden sessions** (binding — this is what keeps "always running" acceptable): when a window is hidden, after `cscode.background.trimAfterSeconds` (default 30 s) dispose live editor *views* (keep documents + view state), drop re-creatable caches, stop UI timers/animations/caret blink/polling, and run a compacting trim (use `IMemoryMonitor.TrimNowAsync(Aggressive)` — this requires merging the **parked Profiling module's** monitor/trim machinery at that point; if it is still parked, implement the minimal trim path: compacting GC + `malloc_trim` + dispose views, and say so). Language servers of a hidden session are stopped after `cscode.background.idleServerTimeoutMinutes` (default 15; 0 = never) and restarted lazily on show; running *debug sessions* keep the process un-evictable. **Hidden processes must idle at ~0 % CPU** (no timers firing without work; file watchers stay to keep the tree fresh but batch work while hidden). **Max resident sessions** `cscode.background.maxResidentSessions` (default 3): beyond it, the least-recently-shown hidden session persists and exits. The warm spare is cheap: services constructed but no workspace, no LSP, trimmed after start-up; `cscode.background.warmSpare` (default true).
* **Session store** (`{UserDataDir}/sessions/<name>.json` + `{UserDataDir}/backups/<name>/…`): JSON, versioned schema, **atomic** writes, debounced autosave (≤ 2 s after a change, and on hide/quit/crash-handler), corruption-tolerant (`.bak`), sessions survive reboots: on login with autostart, `--background` restores the resident set lazily (session processes start hidden only when `cscode.background.restoreOnLogin` = true; otherwise only the spare). Hot-exit backups: dirty document text + encoding/EOL + base file mtime/etag (detect on restore if the file changed on disk meanwhile → conflict prompt), bounded size per session with a clear warning above `cscode.sessions.maxBackupMb` (default 200).
* **UI**: *File ▸ Sessions ▸* Save Session As…, Open Session…, Switch Session (also Quick Launch `session:` mode / command `workbench.action.switchSession`, default `Ctrl+Alt+S`), Rename, Delete, *Close Window (keep running)*, *Quit Session*; window title shows `session — folder`; status bar session indicator (optional); Welcome page lists saved sessions with last-used time.
* **Autostart helpers** (opt-in, never installed silently): `tools/autostart/install-linux.sh` (systemd **user** unit `cscode-background.service` running `cscode --background`, or an XDG autostart `.desktop` file), Windows (per-user Run key / Startup shortcut), macOS (LaunchAgent plist). A Settings toggle "Start CsCode in the background at login" that calls them with confirmation.

## Threading & isolation (binding)
IPC servers and session autosave run on dedicated background lanes; the UI thread only builds the immutable session snapshot (cheap, ≤ 4 ms; large view-state sets captured incrementally) and applies a restored snapshot in ≤ 4 ms slices (open editors lazily: create the *active* tab's view first, others on demand). A wedged or crashed session process never blocks the launcher (connect/handshake timeouts ~300 ms → fall back to starting a fresh process and report it).
