# Module brief — Profiling & memory stability (`CsCode.Profiling` + `tests/CsCode.MemoryTests`)

**Owns:** `src/CsCode.Profiling/**`, `tests/CsCode.MemoryTests/**`, `tools/profile/**`, `docs/MEMORY.md`, the *Profiling* section of `Directory.Packages.props`.
**Implements (Core):** `IMemoryMonitor`, trim orchestration for `IMemoryTrimmable` (`Core/Diagnostics/MemoryContracts.cs`).
**Consumes (Core, via DI):** `IConfigurationService` (`cscode.memory.budgetMb`, `cscode.memory.trimOnIdle`), `IStatusBarService` (optional), `IOutputService` (optional "Memory" channel), `ILoggerFactory`.
**Does not touch:** other modules' source. (You *measure* them later; in this wave the app is still a skeleton, so you build the machinery and validate it on synthetic workloads. The soak suite is designed to be pointed at the real, merged app by the integrator.)

## Goal
"**Well profiled, memory-stable app**" is a headline requirement. Deliver (1) runtime machinery that keeps memory flat and responsive to pressure, (2) a measurement + regression harness that proves it with numbers, (3) GC/runtime configuration chosen by experiment, not folklore.

## MUST
1. **`MemoryMonitor : IMemoryMonitor`** — cheap periodic sampling (default 2 s; adaptive slower when idle) of: working set, private bytes, GC heap size/committed, gen0/1/2 counts, LOH size, total allocated bytes, thread count, plus the RSS of **tracked child processes** (`TrackChildProcess`: read `/proc/<pid>/status` VmRSS on Linux, `Process.WorkingSet64` elsewhere; handle exited pids). In-process runtime metrics via `GC.GetGCMemoryInfo`, `GC.GetTotalMemory(false)`, `GC.GetTotalAllocatedBytes`, `System.Diagnostics.Metrics`/`EventListener` on `System.Runtime` — **the sampler itself must allocate ~nothing** (reuse buffers; assert in a test).
   Publishes `Sampled` events and exposes `Current`. Registers `Meter`/`ActivitySource`-style counters so `dotnet-counters monitor --process-id … --counters CsCode` works (document in `docs/MEMORY.md`).
2. **Pressure policy** — `BudgetBytes` from `cscode.memory.budgetMb` (0 = unlimited): below 70 % nothing; ≥ 70 % → `Trim(Moderate)` on all registered `IMemoryTrimmable`s; ≥ 90 % or sustained growth → `Aggressive` + child-process over-budget callbacks (`TrackChildProcess(..., restartAboveBytes, onOverBudget)`); hysteresis + minimum interval (no trim storms); trims run on a background thread with per-trimmable exception isolation and timing logged; **`TrimNowAsync(level)`**: run trimmables, then `GC.Collect(2, Forced, blocking, compacting)` with `GCSettings.LargeObjectHeapCompactionMode = CompactOnce` and **return pages to the OS** (Linux: `malloc_trim(0)` via P/Invoke guarded for glibc/musl absence; Windows: `SetProcessWorkingSetSize(-1,-1)`/`EmptyWorkingSet`; macOS: no-op) — measure the real effect and document it.
   **Idle trim** (`cscode.memory.trimOnIdle`): after N seconds without UI activity signals (expose `NotifyActivity()`; the shell calls it on input) run an `Idle`-level trim + compacting GC at most once per idle period.
3. **GC / runtime configuration chosen by experiment.** Build a harness (`tools/profile/gc-matrix.sh` + an in-repo synthetic workload app or test) that runs a representative allocation/retention workload (documents of various sizes, token-state-like object graphs, many small short-lived strings, UI-like churn) under combinations of: `System.GC.Concurrent` on/off, `System.GC.ConserveMemory` 0/3/6/9, `System.GC.RetainVM` on/off, `TieredCompilation`/`TieredPGO`/`TC_QuickJitForLoops`/ReadyToRun, `System.GC.Gen0Size`/`GCgen0MaxBudget`, `System.GC.HeapCount` (workstation), `System.Globalization.Invariant` true/false (ICU is ~25–40 MB RSS on Linux — quantify, and note the functional trade-off: culture-sensitive comparison/casing), `DOTNET_gcServer=0`. Record **peak RSS, steady-state RSS, p50/p99 GC pause, CPU time** in `docs/MEMORY.md` as a table, pick the defaults, and encode them as the recommended `runtimeconfig` template in `src/CsCode.Profiling/runtimeconfig.recommended.json` + MSBuild props `build/MemoryDefaults.props` (additive file the integrator imports into `CsCode.App.csproj`). Be explicit about which numbers were measured here (Linux x64, this machine) and which are assumptions.
4. **Leak-detection toolkit** (`CsCode.Profiling.Testing` namespace in this project, usable from any test project): improve on `tests/CsCode.TestDoubles/LeakAssert` (you may extend it, additive only) with: `LeakProbe` (track N instances of type T via `ConditionalWeakTable`/`WeakReference` and assert counts), **heap-census** helper (use `GC.GetGCMemoryInfo`, `GC.GetTotalMemory(true)` snapshots before/after a scenario run N times; assert slope ≈ 0 using linear regression with an explicit noise tolerance and a warm-up phase), **handle/thread/fd census** (`/proc/self/fd`, `/proc/self/task`, `Process.HandleCount`), event-subscription audit (`Emitter<T>.SubscriberCount` assertions through a tiny `IEmitterProbe` pattern if you can do it additively), and a `Soak` runner: `SoakRunner.Run(scenario, duration | iterations, sampleInterval)` → time series (RSS, GC heap, gen2 count, thread count, fd count) + regression report (slope in bytes/iteration and MB/hour, with confidence) and CSV/JSON output under `.scratch/soak/`.
5. **Soak/regression suite** `tests/CsCode.MemoryTests` (xUnit v3, category/trait `Soak`; the default `dotnet test` run executes only the **fast** variants (seconds); the long variants run with the env flags `CSCODE_SOAK=1` and `CSCODE_SOAK_MINUTES=N`): scenarios built from **Core-level primitives now** (document open/edit/close churn through `DocumentManager` + `InMemoryTextDocument`, language-feature registry register/unregister churn, diagnostics set/clear churn, `Emitter` subscribe/unsubscribe churn, contribution registry churn, `MemoryMonitor` + trimmable cycles, simulated child-process tracking, output-channel-like ring buffers at 1M lines) **and a pluggable `IScenario` interface** so the integrator can add UI/LSP/DAP/extension-host scenarios against the real app (headless Avalonia: open/close tabs, scroll, type, switch themes, show/hide tool windows; LSP server start/stop; debug session cycles; extension host restarts) without changing the runner. Provide those app-level scenarios as **ready-to-enable, skipped-until-wired** tests with clear TODO reasons *only if* compile-safe against what exists (otherwise document them in `docs/MEMORY.md` as the integrator's checklist with exact code skeletons).
   Assertions: steady-state heap slope below an explicit threshold after warm-up; RSS plateau; thread/fd counts return to baseline; gen2 collections not growing super-linearly; `MemoryMonitor` sampler allocation ≈ 0 bytes/sample.
6. **BenchmarkDotNet suite** (`tests/CsCode.MemoryTests/Benchmarks/` or a separate `benchmarks/` project you add to the solution): `MemoryDiagnoser` benchmarks for `InMemoryTextDocument.ApplyEdits`, `Glob.IsMatch`, `DocumentSelector.Score`, `LanguageFeatureRegistry.GetProviders`, `Emitter.Fire`, `DiagnosticService.Set/GetAll` — report allocations/op and ns/op in `docs/MEMORY.md`; **fix any hot-path allocation regressions you find in Core** (additive/behaviour-preserving changes only, with the existing Core tests still green — you are explicitly permitted to optimise Core internals for these, nothing else in Core).
7. **Profiling playbook** `docs/MEMORY.md` + scripts in `tools/profile/`: how to take a **GC dump** (`dotnet-gcdump collect -p <pid>`), a **trace** (`dotnet-trace collect --profile gc-verbose`/`dotnet-counters`), dump analysis (`dotnet-dump analyze` → `dumpheap -stat`, `gcroot`), `perf`/`heaptrack` notes for native (Skia) memory, comparing two gcdumps to find growth, `DOTNET_gcTrace`; one-command scripts (`tools/profile/soak.sh`, `tools/profile/gcdump.sh`, `tools/profile/counters.sh`) that install the dotnet tools into `.scratch/tools/dotnet-tools` if missing. Include the **memory budget table** (targets: idle RSS with empty workspace; with 20 open documents; with 1 LSP server; with extension host running; soak growth ≤ 1 MB/h after warm-up) — mark each target `measured` (with the number and how) or `target — not yet measured against the full app`. Never invent a measurement.
8. **`AddCsCodeProfiling(this IServiceCollection)`**: registers `IMemoryMonitor` (singleton, started/stopped with the host via a small `IHostedLifecycle`-style start method the integrator calls), reads config lazily and tolerates missing optional services.

## SHOULD
* Allocation-rate and GC-pause telemetry surfaced as `Metrics` instruments + an optional "Memory" Output channel line every minute; `/proc/<pid>/smaps_rollup` breakdown (anon vs file-backed vs shared) in the diagnostics snapshot to separate managed from native (Skia/ICU) memory; Windows/macOS code paths compile-guarded.
* A **managed-vs-native attribution report** helper (`MemoryBreakdown`) for the About/diagnostics view.
* Analyzer config proposal for IDisposable/event hygiene (CA2000/CA2213 where practical, banned-API list for `static event`/`+= ` on singletons) as `docs/MEMORY.md` appendix — only enable rules that don't drown the build.

## Done when
MUST all implemented and green (fast soak runs included; run one **real ≥ 10-minute soak locally** and put the actual slope/plateau numbers in `docs/MEMORY.md`), GC matrix executed with real measured numbers, playbook written, committed.
