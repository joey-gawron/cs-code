# Module brief — Debug panels (`CsCode.Panels.Debug`)

**Owns:** `src/CsCode.Panels.Debug/**`, `tests/CsCode.Panels.Debug.Tests/**`, `docs/PANELS-DEBUG.md`. Read `docs/briefs/00-common.md` first (rules, threading, memory) — everything there applies.
**Context:** the DAP module (`CsCode.Dap`), shell kit (`CsCode.Ui`) and shell (`CsCode.App`) are already merged into your worktree's base. The Shell/Editor/LSP/DAP/Platform agents are *still working* on their own branches in parallel; you build only these panels against Core interfaces + `CsCode.Ui`. Don't edit their projects.
**Provides:** `IToolWindow` implementations (`CsCode.Ui.IToolWindow`) registered by `AddCsCodeDebugPanels(this IServiceCollection)`. The shell discovers them from DI, creates views lazily and **disposes views when hidden** (`CreateView` contract) — your view-models must therefore be cheap to recreate and fully disposable.
**Consumes (Core, via DI):** `IDebugService`, `IDebugFrameFocus`, `IDebugOutputHistory`, `IDebugSourceContentProvider`, `IBreakpointManager`, `IDebugConfigurationService`, `ICommandService`, `IContextKeyService`, `INavigationService`, `IWindowService`, `IColorThemeService` (via `CsCode.Ui` brush keys). Debug *commands* (`workbench.action.debug.*`) are already registered by the DAP module — do not re-register them; panels only call them or the services.
**Design system:** read `src/CsCode.Ui` (`Theming/WorkbenchColors.cs` + `ThemeApplier` define the `vsc:<colorId>` resource keys — use `{DynamicResource vsc:…}` only, never hard-coded colours; `Icons/Icon` control + `IconPaths.g.cs`; `Threading/UiDispatcher` (coalesced/batched UI posts); `Collections/BulkObservableCollection`; `Text/FuzzyMatcher`).

## Goal
The VS2022 debugging experience: when a session is active, the **Locals, Autos, Watch, Call Stack, Breakpoints, Threads and Debug Console** windows appear, update live, never block the UI, and stay memory-flat across thousands of stops.

## MUST — tool windows (ids and defaults)
| Id | Title | Default location | Notes |
|---|---|---|---|
| `debug.callstack` | Call Stack | Bottom | Threads → frames tree (flat frame list when one thread); current frame arrow; greyed "external code" frames (`presentationHint: subtle/label`); click/double-click selects the frame via **`IDebugFrameFocus`** (moves the editor's stop marker) and opens the source via `INavigationService`; lazy paging of long stacks (`GetStackTraceAsync(startFrame, levels)`); context menu: Copy Call Stack, Show/Hide external code |
| `debug.locals` | Locals | Bottom | variables of the focused frame's first scope(s); lazy expandable tree; paged children (100 per page + "…more" row) |
| `debug.autos` | Autos | Bottom | pragmatic approximation: the frame's non-expensive scopes' variables referenced on the current line if the editor can tell you (optional), else same source as Locals minus `this`/statics; document the approximation |
| `debug.watch` | Watch 1 | Bottom | add expression (inline editor on the empty last row, or Ctrl+Alt+W / command `debug.addToWatch`), edit, delete, drag reorder, refresh on stop/step, errors shown in red with message, expandable results (`variablesReference`), persisted per workspace via `IDebugService.Watches` |
| `debug.breakpoints` | Breakpoints | Bottom | list of source / function / exception breakpoints with **enable checkbox**, file:line, condition/hit-count/log-message badges, adapter verification state (verified ✓ / unverified hollow / moved-line note / failed message from `IBreakpointManager.GetStatus`), delete, delete all, enable/disable all, edit condition inline (`IWindowService.ShowInputBoxAsync`), **Exception Settings** section from `IBreakpointManager.ExceptionFilters`, double-click navigates |
| `debug.threads` | Threads | Bottom | thread list with state (running/stopped), selected-thread switch (`IDebugSession` focused thread), freeze/thaw only if the session supports it |
| `debug.console` | Debug Console | Bottom | scrolling output from `IDebugService.Output` (+ late-subscriber history from `IDebugOutputHistory`), category colouring (stdout/stderr/console/important), **REPL input** at the bottom (evaluate in the focused frame with context `repl`, result appended, history ↑/↓, **completions** via `CompletionsAsync`, multiline with Shift+Enter), clear, filter, auto-scroll lock; **bounded** (≤ 5,000 lines retained, virtualised list) |
All: `AutoShowWhen = "inDebugMode"` for the group (the shell auto-shows/hides), icons from the catalog, `ToggleCommandId` per window (`workbench.debug.action.toggle<Name>`; register these toggle commands only if the shell has not — check `docs/SHELL.md`/code in `CsCode.App` first), correct keyboard navigation (↑↓←→ expand/collapse, Enter edit, Delete remove, F2 rename, Ctrl+C copy value).

## MUST — the variables tree (shared by Locals/Autos/Watch/hover pins)
`VariableNodeViewModel` with **lazy children** (`GetVariablesAsync(variablesReference, start, count)`), paging for large arrays (indexed/named counts), type column, value column with **change highlighting** (red text when the value differs from the previous stop; cleared on next change), value formatting (strings quoted, truncated to 200 chars with "…" + full value in tooltip/copy), **edit value in place** (`SetVariableAsync`; error shown inline), copy value / copy expression / add to watch, "view as hex/decimal" for integers (client-side), `evaluateName` used for watch/copy-expression. **Handle lifetime**: `variablesReference` handles die on resume — cancel in-flight loads on `Continued`/step, drop the whole tree on resume (keep expansion paths by name and re-expand lazily after the next stop, like VS), never hold stale handles. The tree view is **virtualised** (a 1M-element array shows 100 rows, not 1M). Use `BulkObservableCollection` for batched updates.

## SHOULD
Exception Helper popup (on `stopped(reason: exception)`: exception type/message/inner/stack via `exceptionInfo` if the session supports it, "Copy details", "Continue"), Modules window (`module` events), "Pin to source" DataTip is the Editor's job (skip), Debug *Parallel Stacks* no, memory/disassembly no, **Immediate-window style** evaluation is the Debug Console, performance counters no.

## Threading & isolation (binding — ARCHITECTURE §6)
* **Nothing blocks the UI thread.** Every service call is awaited from view-model commands; no `.Result/.Wait/GetResult` (the banned-API analyzer is on and will fail the build). Results are applied in slices ≤ 4 ms via `UiDispatcher.PostBatched`; coalesce bursts of `Output`/`StateChanged` events (≥ 16 ms windows, latest-wins).
* A debuggee that **floods output (1M lines/s)**, an adapter that answers slowly or never, a **1M-element array** expansion, and rapid step-step-step must not stall the UI, grow memory without bound, or show stale data for a previous stop. Test it (hostile fakes + a headless dispatcher heartbeat probe: p99 queue latency < 16 ms, max < 50 ms).
* Every subscription (`IDebugService.*`, `IBreakpointManager.Changed`, `IContextKeyService`) lives in a `DisposableStore` released when the view is hidden/disposed. `LeakAssert` test: show/hide each panel 100× across 20 debug sessions → nothing retained.

## Tests (`tests/CsCode.Panels.Debug.Tests`, xUnit v3 + Avalonia.Headless)
1. View-model unit tests against fake `IDebugService/IDebugSession` (build your own fakes in the test project; `CsCode.TestDoubles` for the rest): lazy expansion, paging, change highlighting, handle invalidation on resume, edit value success/failure, watch add/edit/remove/persist, call-stack selection → `IDebugFrameFocus`, breakpoint list states from statuses, console bounding & history, REPL history/completions, exception helper.
2. Headless UI: render every panel with sample data in the Dark theme (use `CsCode.Ui.ThemeApplier` with `VsThemes` in the test app) → `.scratch/screenshots/debug-*.png` (git-ignored); **Read the PNGs and fix visual defects** (alignment, truncation, contrast, selection colours, icons) until they look like VS2022's debug windows. Keyboard-driven interaction tests.
3. **End-to-end with the real DAP module + real netcoredbg**: reference `CsCode.Dap` (test project only; Panels itself must not reference it), fetch the adapter with `tools/fetch-netcoredbg.sh` (skip with reason if unavailable), build a tiny C# console program in a temp dir, start a real session through `IDebugService`, and assert the **panel view-models** show the real stack frames, real locals (`x`, `s`), update after step-over (changed value highlighted), watch `x + 1` evaluates, breakpoints list shows verified, console shows the program's stdout, everything cleans up (no stray processes).
4. Hostile/responsiveness + leak tests as above.
